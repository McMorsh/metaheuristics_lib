# AGENTS.md

Правила для людей и AI-агентов, которые меняют этот репозиторий.
Цель: минимальные, предсказуемые и проверяемые изменения.
Файл можно использовать как шаблон для Python-проекта: замените имя проекта
и пакета на фактическое.

## Базовый стандарт

Основываемся на [PEP 8](https://peps.python.org/pep-0008/). Дополнительно:

- [PEP 257](https://peps.python.org/pep-0257/) - docstring;
- [PEP 484](https://peps.python.org/pep-0484/) и
  [PEP 526](https://peps.python.org/pep-0526/) - аннотации типов;
- [PEP 585](https://peps.python.org/pep-0585/) - встроенные generic-типы;
- [PEP 604](https://peps.python.org/pep-0604/) - объединения через `|`;
- [PEP 621](https://peps.python.org/pep-0621/) - метаданные проекта в
  секции `[project]`; настройки инструментов хранятся в `pyproject.toml`.

Если правило ниже не описывает случай, действует PEP 8. Отступления от PEP 8
допустимы только явные и зафиксированные в `pyproject.toml`.

Документация проекта (`README.md`, `AGENTS.md`), docstring, комментарии
и сообщения исключений пишутся на русском языке. Имена в коде - на
английском, без транслитерации. Служебные логи - на английском.

Базовый стек: Python 3.12+, `numpy`, `pytest`, `ruff`, `mypy`. `mpi4py`
подключается как опциональная зависимость. Не используйте синтаксис новее
минимальной поддерживаемой версии.

## Форматирование

- Источник правил - `ruff format` в режиме, совместимом с Black. Настройки
  хранятся в `pyproject.toml`.
- Отступ 4 пробела. Табы запрещены.
- Длина строки 79 по PEP 8. В `pyproject.toml` задано `line-length = 79`.
- Переносы строк делайте по PEP 8: выравнивание по открывающей скобке или
  висячий отступ 4 пробела. Конкретные переносы расставляет `ruff format`.
- Строки, которые форматтер не может разбить (длинные литералы, URL),
  переносите вручную. Если разбить нельзя, используйте `# noqa: E501`
  с причиной.
- Кодировка UTF-8, перевод строки LF, завершающий перевод строки в конце файла.
- Двойные кавычки. Одинарные допустимы, только если внутри строки есть
  двойные кавычки.
- Одна инструкция на строку. Точка с запятой как разделитель запрещена.
- Две пустые строки между определениями верхнего уровня, одна - между
  методами класса.
- Пробелы вокруг бинарных операторов и после запятых по PEP 8. Без пробелов
  внутри скобок и перед `(` при вызове.
- В простых срезах пробелов вокруг двоеточия нет: `x[1:2]`. В сложных
  выражениях пробелы симметричны: `x[lower + 1 : upper + 1]`.
- В аннотированных параметрах по умолчанию пробелы вокруг `=` есть:
  `def f(x: int = 0)`. В неаннотированных параметрах и именованных аргументах
  пробелов нет: `def f(x=0)`, `f(x=1)`.
- Переносы, выравнивание и запятые в многострочных литералах расставляет
  форматтер. Не выравнивайте код вручную.
- Предпочитайте короткие функции. Если функция длиннее примерно 40 строк,
  подумайте, можно ли разделить её без потери читаемости.
- Глубина вложенности - не больше трёх уровней. Используйте ранний выход.
- Именованные константы вместо магических чисел.
- `is None` и `is not None` вместо `== None` и `!= None`.
- `if not items` вместо `if len(items) == 0`.
- f-строки вместо `%` и `str.format`. Не оставляйте f-строки без подстановок.
- Генераторы и включения вместо `map` и `filter`, если это читается проще.
  Не вкладывайте больше двух циклов во включение.
- Для новых файлов используйте `pathlib.Path`, а не `os.path`.
- Дробные числа сравнивайте через `math.isclose` или `pytest.approx`, не через
  `==`.

### Порядок импортов

1. `from __future__ import ...`, если используется.
2. Стандартная библиотека.
3. Сторонние библиотеки (`numpy`, `mpi4py`, `matplotlib`).
4. Модули проекта (`core`, `utils`, `problems`, `algorithms`).

- Группы разделяйте одной пустой строкой, внутри группы сортируйте по алфавиту.
- Один модуль на строку: `import os, sys` запрещён. Несколько имён в
  `from module import a, b` допустимы.
- Используйте абсолютные импорты. Не смешивайте в проекте схемы `core...` и
  `metaheuristics_lib.core...`. Текущая раскладка плоская: пишите
  `from core...`, `from utils...`. Вариант `from metaheuristics_lib...`
  появится только после выделения пакета.
- Запрещены `from module import *`.
- Не оставляйте неиспользуемые импорты.
- Тяжёлые опциональные зависимости (`mpi4py`, `matplotlib`) импортируйте в
  модуле, который их реально использует, или лениво внутри функции. Импорт
  `core` и `algorithms` не должен требовать MPI или matplotlib.

### Модули и пакеты

- Имена файлов и каталогов: snake_case, строчные буквы, без пробелов и русских
  символов.
- Параллельные варианты алгоритма: суффиксы `_mp` и `_mpi`, как в существующем
  коде.
- `__init__.py` содержит только явные реэкспорты и `__all__`. Никакой настройки
  логов, чтения файлов и других побочных эффектов при импорте.
- Точка входа скрипта защищена `if __name__ == "__main__":`.
- Циклические импорты запрещены. Общие типы и протоколы держите в `core/`.
- Один модуль - одна ответственность. Реализации алгоритмов - в
  `algorithms/<name>/`, задачи - в `problems/`, общие функции - в `utils/`.
- Не называйте модуль `test.py` внутри пакета: при явном запуске pytest
  примет его за тест, а имя путается с тестовыми модулями. Тесты лежат
  в `tests/`.

## Имена

| Сущность | Стиль | Пример |
| --- | --- | --- |
| Пакеты и модули | snake_case | `artificial_bee_colony.py` |
| Классы и исключения | PascalCase | `BaseAlgorithm`, `ValidationError` |
| Функции и методы | snake_case, глагол | `get_result` |
| Локальные переменные и параметры | snake_case | `max_iter`, `best_fitness` |
| Константы уровня модуля | UPPER_CASE | `DEFAULT_POPULATION_SIZE` |
| Приватные атрибуты | `_` + snake_case | `_cache` |
| Type alias | PascalCase | `Position`, `Fitness` |
| Булевы переменные | `is_`, `has_`, `can_` | `is_converged` |
| Члены Enum | UPPER_CASE | `Color.RED` |
| Тестовые функции | `test_` + поведение | `test_sphere_zero` |
| Параллельные модули | `_mp` или `_mpi` | `..._mpi.py` |

Имена на английском, без транслитерации и лишних сокращений. Общепринятые
сокращения допустимы: `idx`, `dim`, `max_iter`, `num_agents`. Аббревиатуры
пишите как обычные слова: `mpi_rank`, `json_config`.

Булевы переменные и методы называйте так, чтобы имя читалось как условие:
`is_converged`, `has_best`, `can_parallel`.

Не перекрывайте встроенные имена: `list`, `dict`, `set`, `id`, `type`, `iter`,
`next`, `input`, `sum`, `min`, `max`, `open`. Одна буква допустима только для
координат, индексов и размеров: `x`, `y`, `n`, `i`, `j`.

Публичные имена не переименовывайте без явной просьбы: это ломает API и
примеры.

## Типы и аннотации

- Аннотируйте публичные функции, методы, поля dataclass и возвращаемые
  значения. Приватные функции аннотируйте, если это помогает читать код.
- Используйте встроенные generic-типы: `list[int]`, `dict[str, float]`,
  `tuple[int, ...]`.
- Для `None` используйте `X | None`, а не `Optional[X]`.
- Для параметров-коллекций используйте абстракции из `collections.abc`:
  `Sequence`, `Iterable`, `Mapping`, `Callable`.
- Для массивов используйте `numpy.typing.NDArray[np.float64]`; в legacy-коде
  допустим `np.ndarray`. Форму, размерность и dtype описывайте в docstring.
- `Any` допустим только на границе с внешним кодом. Внутри проекта используйте
  `Protocol`, `TypeVar` или конкретные типы.
- Не дублируйте типы в docstring, если есть аннотации.
- Не используйте `# type: ignore` без кода ошибки и причины. Формат:
  `# type: ignore[arg-type]  # причина`.
- Новые модули не должны ухудшать проверку `mypy`. Цель - `strict = true`;
  минимум - для `core/`, `utils/` и `problems/`.

## Классы и данные

- Для структур данных используйте `@dataclass`. Для неизменяемых значений -
  `@dataclass(frozen=True)`.
- Интерфейсы описывайте через `abc.ABC` и `@abstractmethod` или через
  `typing.Protocol`, если наследование не нужно.
- Предпочитайте композицию наследованию. Наследование - только для настоящего
  отношения "является".
- Поля, которые не являются частью публичного контракта, начинайте с `_`.
- Не создавайте тривиальные getter и setter. Используйте свойства, только если
  есть вычисление, проверка или ленивая инициализация.
- Изменяемые значения по умолчанию запрещены: в функциях используйте `None`
  и создавайте объект внутри, в dataclass - `field(default_factory=list)`.
- Конструктор проверяет инварианты, но не выполняет ввод-вывод и не запускает
  вычисления.
- Не храните изменяемое состояние в атрибутах класса. Оно должно быть в
  экземпляре.
- Для отладочного вывода реализуйте `__repr__`; для dataclass он уже есть.
- Не используйте `__del__` для освобождения ресурсов. Используйте контекстные
  менеджеры.

## Ошибки и ресурсы

- Поднимайте конкретные исключения: `ValueError`, `TypeError`, `RuntimeError`,
  а не `Exception`.
- Сообщение исключения должно содержать значение и ожидание:
  `"Параметр dim должен быть положительным, получено 0"`.
- Не используйте `except:` и `except Exception: pass`. Перехватывайте только те
  исключения, которые умеете обработать.
- Не теряйте исходную ошибку: `raise RuntimeError("...") from err`.
- Проверяйте входные данные на границах модуля: размерность, форма массива,
  границы, `agents > 0`, `max_iter >= 1`.
- `assert` допустим только для внутренних инвариантов. Для проверки
  пользовательских данных используйте исключения: `python -O` удаляет
  `assert`.
- Файлы, сокеты, блокировки и пулы открывайте через `with`.
- Библиотечный код поднимает исключения, а не печатает и не завершает процесс.
  `print` и `sys.exit` допустимы только в `examples/` и `__main__`.
- Не перехватывайте `KeyboardInterrupt` и `SystemExit`.
- Для устаревшего поведения используйте
  `warnings.warn(..., DeprecationWarning, stacklevel=2)`.

## Параллельные вычисления

- Функции для `ProcessPoolExecutor` и `multiprocessing` должны быть определены
  на верхнем уровне модуля и быть picklable. Лямбды, замыкания и локальные
  функции не подходят.
- Точка входа скрипта защищена `if __name__ == "__main__":`. На Windows и macOS
  используется spawn, поэтому без защиты процессы зацикливаются.
- `max_workers` задавайте явно. Не запускайте больше процессов, чем ядер, если
  задача CPU-bound.
- Не делите изменяемое состояние между процессами. Возвращайте результат через
  `Future` или очередь.
- В MPI все ранги должны вызывать коллективные операции (`scatter`, `gather`,
  `bcast`, `reduce`) в одном порядке.
- Ввод-вывод и итоговый результат печатает только rank 0. Остальные ранги не
  пишут в общий поток.
- Результат не должен зависеть от числа процессов. Сид каждого ранга выводите
  из общего сида детерминированно, например через
  `numpy.random.SeedSequence(seed).spawn(size)[rank]`, а результаты сортируйте
  или собирайте в фиксированном порядке.
- Для новых вычислений используйте `numpy.random.default_rng(seed)`, а не
  глобальный `np.random.seed`. Генератор передавайте явно.
- Обрабатывайте пустые чанки: `np.array_split` может вернуть пустые массивы,
  если процессов больше, чем элементов.
- Ошибку воркера пробрасывайте наружу. Не глотайте её и не возвращайте `None`
  вместо результата. `None` на не-root ранге - допустимое служебное значение,
  но он не должен маскировать ошибку.
- Тестируйте параллельный код с одним и с несколькими процессами. Для MPI
  используйте `pytest.importorskip("mpi4py")` и отдельную метку `integration`.

## Комментарии и docstring

- В начале модуля - docstring с назначением.
- Публичные классы и функции документируйте. Приватные - только если логика
  неочевидна.
- Стиль docstring - Google (`Args`, `Returns`, `Raises`, `Yields`,
  `Attributes`). Новый код документируйте в Google-стиле. Если модуль уже
  использует reST, не смешивайте стили в одном файле; перевод модуля -
  отдельная задача.
- Первая строка - короткое описание в форме третьего лица: "Возвращает ...",
  "Создаёт ...". Заканчивайте точкой. Это осознанное отступление от
  повелительного наклонения PEP 257, принятое для русских docstring.
- Для многострочного docstring: краткое описание, пустая строка, детали,
  закрывающие кавычки на отдельной строке.
- В `Args` не повторяйте типы, если есть аннотации. Указывайте единицы,
  диапазон и направление параметра.
- `Returns` добавляйте, если смысл возвращаемого значения не очевиден.
  `Raises` - для исключений, которые являются частью контракта.
- Комментарий объясняет причину, ограничение или неочевидную математику, а не
  пересказывает код.
- Не оставляйте закомментированный код. Для истории есть Git.
- Не используйте декоративные разделители, эмодзи, маркетинговые прилагательные
  и шаблонные фразы.
- Не используйте длинные тире U+2014 и U+2013. Только дефис или перестроенная
  фраза.
- TODO: `# TODO(username): ...`.
- Устаревший комментарий считается ошибкой. Меняете поведение, меняйте
  docstring и комментарий.

```python
# Плохо: пересказывает код.

counter += 1

# Хорошо: объясняет, почему индекс сдвинут.
# Внешний формат использует индексы с единицы, поэтому адаптируем счётчик.
index = counter + 1
```

## Тесты

Тесты лежат в `tests/`, запускаются через `pytest`. Имена файлов отражают
модуль: `tests/test_bee_colony.py`, `tests/test_problems.py`,
`tests/test_utils.py`.

Правила:

- Файлы: `tests/test_<модуль>.py`. Функции: `test_<поведение>`.
- Один тест проверяет одно поведение. Имя описывает ожидаемый результат:
  `test_sphere_returns_zero_at_origin`.
- Соблюдайте схему arrange-act-assert. Подготовка, действие и проверка должны
  читаться отдельно.
- Для набора однотипных случаев используйте `pytest.mark.parametrize`.
- Дробные числа сравнивайте через `pytest.approx` или
  `numpy.testing.assert_allclose`. Не сравнивайте `float` через `==`.
- Тесты детерминированы: без `sleep`, без зависимости от времени, сети, порядка
  тестов и состояния внешних устройств.
- Случайность фиксируйте сидом. Для нового кода используйте
  `numpy.random.default_rng(seed)`.
- Файлы создавайте в `tmp_path`, а не в корне репозитория.
- Не тестируйте приватные детали. Проверяйте публичный контракт.
- Фикстуры держите в `conftest.py`. Не выполняйте тяжёлую работу на уровне
  модуля.
- Тесты не должны зависеть от порядка запуска и оставлять после себя файлы.
- Ключевая логика (`core/`, `utils/`, `problems/`, `algorithms/`) покрывается
  тестами. Демонстрационные скрипты в `examples/` можно не покрывать.
- Параллельные тесты помечайте `@pytest.mark.integration` и запускайте
  отдельно: `pytest -q -m integration`. Если `mpi4py` не установлен,
  используйте `pytest.importorskip("mpi4py")`.

Пример:

```python
import numpy as np
import numpy.typing as npt
import pytest

from problems.continuous import sphere


@pytest.mark.parametrize(
    ("point", "expected"),
    [
        (np.array([0.0, 0.0]), 0.0),
        (np.array([1.0, 2.0]), 5.0),
    ],
)
def test_sphere_returns_sum_of_squares(
    point: npt.NDArray[np.float64],
    expected: float,
) -> None:
    assert sphere(point) == pytest.approx(expected)


def test_sphere_rejects_empty_vector() -> None:
    with pytest.raises(ValueError, match="не должен быть пустым"):
        sphere(np.array([]))
```

## Зависимости и конфигурация

- Единый источник метаданных - `pyproject.toml` по PEP 621; настройки
  инструментов также хранятся в нём.
- Зависимости времени выполнения держите минимальными. `numpy` обязателен,
  `mpi4py` и `matplotlib` - опциональные extras.
- Не добавляйте зависимость без необходимости. Сначала проверьте стандартную
  библиотеку и уже подключённые пакеты.
- Указывайте нижние границы версий, а не `*`. Для приложений допустим
  lock-файл.
- `requirements.txt` не дублирует `pyproject.toml`. Если он нужен, генерируйте
  его из `pyproject.toml`.
- Виртуальное окружение `.venv` создаётся локально и не коммитится.
- Секреты, токены и локальные пути не попадают в репозиторий. Используйте
  переменные окружения.
- В `.gitignore` должны быть `__pycache__/`, `*.py[cod]`, `.venv/`,
  `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `dist/`, `build/`,
  `*.egg-info/`, логи и сгенерированные графики.

Пример `pyproject.toml`:

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "metaheuristics-lib"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["numpy>=1.26"]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.10"]
plot = ["matplotlib>=3.8"]
mpi = ["mpi4py>=4"]

[tool.setuptools.packages.find]
include = ["core*", "utils*", "problems*", "algorithms*"]
namespaces = true

[tool.ruff]
line-length = 79
target-version = "py312"

[tool.ruff.lint]
select = ["E4", "E7", "E9", "E501", "F", "I", "N", "UP", "B", "SIM", "RUF"]
ignore = ["RUF001", "RUF002", "RUF003"]  # кириллица в тексте - норма проекта

[tool.mypy]
python_version = "3.12"
strict = true

[[tool.mypy.overrides]]
module = ["matplotlib.*", "mpi4py.*"]
ignore_missing_imports = true

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
markers = ["integration: тесты с MPI или несколькими процессами"]
addopts = "-ra -m 'not integration'"
```

`E501` включён: длина строки 79 контролируется линтером. Строки, которые
форматтер не может разбить, переносите вручную; для неизбежных длинных URL
и литералов используйте `# noqa: E501` с причиной. Список правил расширяйте
по мере миграции (`D`, `ANN`, `PT`, `A`, `PTH`), но не включайте их без
per-file ignores для legacy-кода.

Если legacy-файл уже содержит нарушения выбранных правил, `ruff check` на нём
будет падать. Это исправляется в рамках общей задачи миграции: либо нарушения
устраняются, либо для файла добавляется `per-file-ignores` до его перевода
на новые правила.

`strict` в mypy действует глобально, даже если записан в per-module override.
Включайте его в `[tool.mypy]`, а legacy-модули исключайте через baseline или
`ignore_errors`.

Пример соответствует текущей плоской раскладке: `core` и `utils` - обычные
пакеты, `algorithms` и `problems` подключаются как namespace-пакеты. При
выделении отдельного пакета `metaheuristics_lib/` обновите `include` и импорты.

## Сборка и проверка

Команды ниже проверены на текущем состоянии проекта. Полный прогон
занимает несколько секунд; запускайте его перед завершением задачи.

Linux и macOS:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -U pip
pip install -e ".[dev,plot]"
ruff check .
ruff format --check .
mypy .
pytest -q
```

Windows PowerShell:

```powershell
py -3 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -U pip
pip install -e ".[dev,plot]"
ruff check .
ruff format --check .
mypy .
pytest -q
```

Интеграционные тесты с реальным пулом процессов запускайте отдельно:

```bash
pytest -q -m integration
```

Запуск примеров:

```bash
python -m examples.run_serial --iterations 20 --agents 10 --runs 2
python -m examples.run_mp --iterations 20 --agents 10 --processes 1 2
mpiexec -n 4 python -m examples.run_mpi --iterations 20 --agents 10
```

`python -m` добавляет корень проекта в `sys.path`, поэтому импорты
`from core...` работают без `PYTHONPATH`. `examples/run_mp.py` использует
`multiprocessing`, а `examples/run_mpi.py` - MPI. Графики сохраняются в
`plots/` или в каталог из `--output-dir`.

Перед запуском установите `numpy` и `matplotlib` (extra `plot`). Для MPI
нужны `mpi4py` и системный MPI.

Перед завершением задачи:

1. Запустите `ruff check .` и `ruff format --check .`.
2. Запустите `mypy .`.
3. Запустите `pytest -q`; для изменений в multiprocessing -
   `pytest -q -m integration`.
4. Запустите затронутый пример или скрипт.
5. Просмотрите `git diff`: в нём не должно быть отладочного вывода, кэшей,
   графиков, секретов и случайных переименований.

Массовый реформат и изменение поведения - отдельные коммиты, не смешивайте
их в одной задаче.

## Git

- Формат коммитов: Conventional Commits, английский императив, до 50 символов в
  заголовке, тело до 72 символов.
- Один коммит - одно логическое изменение. Не смешивайте фичу, рефакторинг и
  форматирование.
- Не добавляйте в репозиторий `__pycache__/`, `.venv/`, `.pytest_cache/`,
  `.mypy_cache/`, `.ruff_cache/`, логи, графики, личные заметки и секреты.
- Агент не коммитит, не пушит, не делает rebase и не меняет историю без явной
  просьбы.
- Перед push синхронизируйтесь с `origin/main`. Если ветки разошлись,
  согласуйте rebase или merge; без явного согласия историю не переписывайте.
